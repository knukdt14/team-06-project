# 문서처리·검색 최종 리포트 (Document Processing & Retrieval)

- **담당:** 이수민 · **날짜:** 2026-07-27
- **시스템:** 2025 연말정산 PDF(418쪽) 기반 RAG

---

## 1. 무엇을 했나

문서처리 파트(PDF 로드·분할·전처리·저장)를 **한 번에 하나씩 바꾸고, 측정하고, 나쁘면 롤백**하는 방식으로 개선했다.

- **검색 채점기 `eval_retrieval.py` 자체 제작** — LLM 없이 Hit@k/MRR 측정 (팀 공용 측정 도구)
- 개선 실험: chunk_size / overlap / **반복 머리말 제거** / **표 전처리(Markdown)** / section 청킹
- **저장 전략 비교**: Chroma vs FAISS, FAISS Flat vs HNSW

## 2. 개선 결과 (검색 Hit@3)

> ⚠️ 프로젝트 중반, 팀장이 채점 기준을 **"정답 1페이지" → "정답 여러 페이지(multi-gold)"** 로 공정하게 개선함. 두 기준 모두로 표기한다.

| 단계 | 옛 기준 (정답 1개) | 새 기준 (multi-gold) |
|---|---|---|
| baseline (chunk 1000) | 0.154 | 0.769 |
| chunk 500 | 0.385 | **0.923** |
| + 머리말 제거 | 0.462 | 0.923 (MRR↑ 0.81, 중복 19→7) |
| + 표 전처리(Markdown) | 0.538 | — (앙상블 입력으로 이관) |

**해석**
- **chunk 500**이 핵심 개선 (새 기준에서 0.769 → 0.923).
- **머리말 제거**는 새 기준에서 Hit 대신 **정답 순위(MRR)·검색 다양성**을 개선.
- 같은 개선이 채점 기준에 따라 다르게 보임 → "우리 검색이 원래 답을 잘 찾고 있었음"을 확인.

## 3. 저장 전략 비교 (채점 항목: 여러 저장 전략)

동일 임베딩·청크로 공정 비교 (chunk500/ov100, ko-sroberta):

| 엔진 | 인덱스 | Hit@3 | 빌드 | 검색/질의 | 디스크 |
|---|---|---|---|---|---|
| Chroma | HNSW | 0.923 | 1.5초 | 1.2ms | 17.8MiB |
| FAISS | Flat | 0.923 | **0.05초** | **0.13ms** | **4.3MiB** |
| FAISS | HNSW | 0.923 | 0.05초 | 0.06ms | 4.6MiB |

**결론:** 이 규모(~1,100 벡터)에선 **품질 동일.** FAISS Flat이 빌드·검색·용량 우위지만, Chroma도 검색 1.2ms로 병목 아님 → **운영 편의(자동 영속화·메타데이터)면 Chroma, 자원 최소면 FAISS Flat.** 근사 인덱스(HNSW)는 대용량에서 유리하나 현 규모엔 차이 미미.

## 4. 방법론 (발표 강조 포인트)

- **한 번에 하나만 바꾸고 측정** → 원인을 명확히 설명 가능
- **가설 검증:** 전처리(머리말 제거) 후 overlap·chunk를 **재확인** (초기 결론이 여전히 유효한지)
- **이상치 재검증:** overlap 점수 널뛰기·chunk1000=0 같은 이상 결과를 **직접 재현·검증** (숫자를 그냥 믿지 않음)
- **채택/미채택 판정:** section 청킹·Markdown 로더는 **회귀 확인 후 미채택/이관**

## 5. 남은 문제 → 검색팀(이희영) 이관

- **Q10(표준세액공제)만 실패.** 정답이 188쪽에 있으나 유사도 순위 **33위** — 질문("아무것도 신청 안 하면")과 답("표준세액공제")의 **임베딩 매칭 gap**. top_k·MMR·hybrid로 해결 안 됨.
- **처방:** 자동/일반 **query rewrite**(핵심 제도명 보강) + RRF + 페이지 중복제거 → **이희영**. (상세: `handoff_ensemble.md`)
- ⚠️ Q10 답을 손으로 넣으면 **과적합** → **평가 질문 확대 후 일반화 검증** 필요(팀장).
