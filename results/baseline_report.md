## 2. 베이스라인 설정

| 항목 | 값 |
|---|---|
| chunk_size / overlap | 1000 / 200 |
| top_k | 3 |
| 임베딩 | HuggingFace `jhgan/ko-sroberta-multitask` (로컬) |

| 총 페이지 / 청크 | 418 / 635 |

## 3. 측정 지표 2종

1. **검색 Hit@k / MRR** — 정답이 있는 페이지가 검색된 top-k에 포함되는지 (API·비용 없이 측정, 빠른 반복용)
2. **BERTScore F1** — 최종 답변이 모범답안과 얼마나 유사한지 (Gemini 사용, 발표용 지표)

## 4. 결과

### 4-1. 베이스라인
| 지표 | 값 |
|---|---|
| 검색 Hit@3 | 0.154 (13개 중 2개) |
| 검색 MRR | 0.115 |
| BERTScore F1 | 0.6961 |
| 평균 응답시간 | 6.56초 |

### 4-2. 파라미터 실험 (검색 채점, API 불필요)
| 실험 | 청크 수 | Hit@k | Hit rate | MRR |
|---|---|---|---|---|
| baseline (1000/200, k=3) | 635 | 2/13 | 0.154 | 0.115 |
| k10 (1000/200, **k=10**) | 635 | 3/13 | 0.231 | 0.126 |
| **cs500 (500/100, k=3)** | 1,132 | **5/13** | **0.385** | 0.192 |
| cs300 (300/50, k=3) | 1,725 | 4/13 | 0.308 | **0.231** |

### 4-3. 해석 (중요)

1. **top_k를 3→10으로 늘려도 거의 안 오름** (0.154→0.231) → 정답 페이지가 애초에 검색 안 됨 = **순위 문제가 아니라 검색 자체 문제.**
2. **chunk_size를 줄이니 크게 오름** (500에서 최고) → **"한 페이지에 여러 공제 항목이 뭉쳐 있어 큰 청크가 희석되는 문제"가 데이터로 확정.** (300은 너무 잘게 쪼개져 오히려 손해)
3. **⚠️ 뉘앙스 (팀 논의 필요):** 정답 페이지 기준을 "앞쪽 요약 페이지(4·5·6 등)"로 잡아서 Hit@3이 낮게 나옴. 하지만 실제로는 LLM이 **뒤쪽 상세 페이지**에서 답을 찾아 **10/13 문항에 정상 답변**함 (BERTScore 0.72~0.78).
   - **진짜 실패(“문서에서 찾을 수 없습니다”)는 3개뿐:** **Q1**(월세 금액), **Q9**(70세 경로우대), **Q10**(표준공제)
   - 👉 **팀 논의:** 검색 정답 기준을 "요약 페이지"로 볼지, "답이 있는 아무 페이지"로 볼지? (이희영/팀장과 정렬 필요)

### 4-4. cs500 최종 확인 — 검색·답변 둘 다 개선 ✅

| 설정 | 검색 Hit@3 | BERTScore F1 | 응답시간 |
|---|---|---|---|
| baseline (1000/200) | 0.154 | 0.6961 | 6.56초 |
| **cs500 (500/100)** | **0.385** | **0.7423** | 7.21초 |

→ `chunk_size=500`이 **검색과 최종 답변 품질을 모두 개선.** 채택 근거 확보.
